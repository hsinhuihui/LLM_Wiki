⚖️ 單點覆蓋 (Ctrl+S) vs 狀態快照 (Snapshot)

一般軟體的儲存是一鍵覆蓋，而 Git 則是將每次變更記錄為不可篡改的 DAG 節點。

核心資料結構

不可篡改的節點鏈

• Ctrl+S 的致命缺點：狀態單一且覆蓋即蒸發，歷史無法重現。
• Git 快照機制：每次提交皆生成獨立的校驗節點（Hash），節點之間具備指向父節點的關聯，保證歷史永遠可追溯。

💡 心法：Git 不是「存檔」，而是將專案在該瞬間的完整狀態「打上一記時間戳快照」。

🏛️ 三大核心空間狀態流向圖

工作區（修改）➔ 暫存區（挑選裝箱）➔ 版本庫（永久存檔）的標準資料管道。

生活化比喻

寄件快遞打包箱

• 工作區：你的辦公桌，塗塗改改毫不受拘束。
• 暫存區：寄件打包箱。只有你手動放進箱子裡的檔案，才會在封箱時被永久提交。
• 版本庫：已蓋上戳印、無法篡改的物流存檔。

# 日常標準三步曲
git status           # 檢視狀態
git add index.html   # 挑選檔案放入暫存區
git commit -m "feat: 新增首頁導航"

🚦 git status 檔案狀態座標分析

終端機中的「紅字」與「綠字」代表檔案當前在三大空間圖中的精確座標。

狀態判讀心法

紅燈停，綠燈行

• 紅色檔案：代表修改僅存在於本機工作區，Git 尚未準備將其納入歷史。
• 綠色檔案：代表已成功執行 git add 進入暫存區，按下 commit 即會正式封存。
• 精簡檢視：可使用 git status -s 檢視 M、?? 狀態標記。

📌 避坑提醒：執行 commit 之前，務必再次用 git status 檢查綠色清單是否完全符合預期！

⚠️ 新手空間防雷陷阱與救援指南

切換分支前的未存檔風險，以及不小心卡在 Vim 終端機時的標準逃脫手冊。

操作守則

保持工作區乾淨

• 切換分支黃金律：切換前確保 git status 乾淨無未存修改，或使用 git stash 暫存。
• Vim 逃脫口訣：先按 Esc 切換指令模式，輸入 :wq + Enter 存檔退出。

💡 建議：平時養成 git commit -m "訊息" 一鍵帶訊息的好習慣，避免意外開啟預設編輯器。

🔬 Commit 節點的底層解剖圖

Commit 不僅僅是一段文字，而是一個指向樹狀目錄與父節點的完整資料物件。

不可篡改保證

Merkle DAG 快照機制

• 40 碼 SHA-1 Hash：由樹狀內容、時間、作者與 Parent Hash 共同計算而成。
• 骨牌效應：只要修改過去任何一個字母，該節點及後續所有節點的 Hash 就會完全改變，杜絕暗中竄改。

💡 檢視指令：使用 git cat-file -p HEAD 可以直接在終端印出此底層物件！

🏷️ 分支（Branch）的本質：輕量貼紙指標

分支絕不是複製整包專案，它只是一個記錄 40 碼 Hash 的輕量文字指標。

破解迷思

建立分支只要 1 毫秒

• 傳統版本控制：開分支需整包拷貝資料夾，耗時耗硬碟。
• Git 分支：只在磁碟中建立一個 41 bytes 的文字檔，寫入當前 Commit 的 Hash。
• 成本近乎為零：因此鼓勵隨時開分支做實驗，用完即拆。

# 建立並切換至新功能分支
git switch -c feature-login

🔦 HEAD 聚光燈指標與工作焦點

HEAD 是當前閱讀與編輯的聚光燈，它告訴 Git「你現在正在哪裡看世界」。

HEAD 指向原則

雙層參照機制

• 正常狀態：HEAD 指向分支（如 ref: refs/heads/main），分支再指向 Commit 節點。
• 切換分支：執行 git switch feature 時，HEAD 撕下並改貼到 feature 分支上。
• 分離頭指標 (Detached HEAD)：若直接 checkout 某個 Hash，HEAD 會脫離分支孤立指向該節點。

💡 最佳實踐：始終透過 git switch 在具名分支間切換，避免落入 Detached HEAD 狀態。

⏩ 線性推進演進圖：Commit 如何推動指標

每次按下 Commit，Git 在底層完成的 3 步拓撲轉移動作。

底層 3 步拓撲

提交背後的連鎖反應

1. 建立新節點：將暫存區打包為新 Commit (C3)。
2. 指向父節點：C3 自動將 Parent 設為原本的 HEAD (C2)。
3. 滑動分支指標：當前分支 main 指標向前滑至 C3，HEAD 隨之同步推進。

📌 總結：Git 的歷史不是往前蓋樓，而是新節點反向拉住舊節點的鏈結串列。

🌿 分支分岔拓撲圖 (Branch Divergence)

平行開發的核心架構：主幹與功能分支如何各自獨立向前推進。

平行開發優勢

彼此隔離，互不干擾

• 主幹安全：main 可隨時修復線上 bug（C5）。
• 大膽實驗：feature 在獨立軌道上開發新功能（C3、C4），完全不影響穩定版本。
• 後續命運：當功能完成時，透過「合併（Merge）」將兩條軌道重新收斂。

# 檢視分支分岔樹狀圖
git log --oneline --graph --all

⚡ 合併模式 A：Fast-forward 快進合併

最純粹的合併：當主幹自始至終沒有新變更時，指標直接順風滑動。

觸發條件與特點

無須生成新節點

• 觸發時機：main 在分岔之後「完全沒有任何新 Commit」。
• 動作本質：Git 判定兩者處於同一線性序列，直接將 main 標籤移動到 feature 頂端。
• 好處：歷史保持完美的純線性，零額外冗餘節點。

git switch main
git merge feature   # 輸出：Fast-forward

💎 合併模式 B：三方合併 (3-Way Merge)

當兩條分支各自有新提交時，Git 尋找共同祖先並生成具「雙親」的專屬節點。

三方比較機制

何謂「三方 (3-Way)」？

• Base：共同祖先 C2。
• Ours：當前所在分支 C5（main）。
• Theirs：準備併入的分支 C4（feature）。
• Merge Commit 特性：C6 同時擁有兩個父節點（C5 與 C4），形成經典菱形拓撲。

💡 知識點：只要兩者修改的不是同個檔案的同一行，Git 就會自動完成三方合併！

⚡ 合併衝突排查與拓撲解套 4 步驟

當兩條分支修改了同一行代碼時，Git 會暫停並在檔案中留下標準衝突標記。

標準 4 步解套 SOP

1. 定位衝突：使用 git status 查看 both modified 檔案。
2. 人工決策：開啟編輯器，與團隊討論取捨，刪除符號標記。
3. 標記解決：執行 git add <檔案> 將修正結果放入暫存區。
4. 完成提交：執行 git commit 完成具備雙親的 Merge 節點。

🛡️ 一鍵後悔藥：若解衝突途中想直接放棄還原，可輸入 git merge --abort。

🌐 本機單兵拓撲 vs 雲端中繼拓撲

Git 本機工具與 GitHub 雲端代碼託管平台的職責架構劃分。

分散式威力

無網路也能完整工作

• Git（本機引擎）：誕生於 2005 年，每台電腦都保存有 100% 完整的歷史快照，斷網時照樣能 commit、開分支與查看 log。
• GitHub（雲端舞台）：提供多人間的遠端中繼同步、PR 程式碼審查與專案 Issue 追蹤。

💡 總結：Git 是你的單機畫具箱，GitHub 是向全世界展示作品的雲端藝廊。

🚀 首次打通遠端管線的 6 步驟

建立本地專案並成功推送至 GitHub 雲端倉庫的標準操作流。

關鍵參數解析

• git remote add origin <URL>：為遠端網址取一個代名詞「origin」。
• git branch -M main：將主分支統一命名為現代標準的 main。
• git push -u origin main：-u 綁定預設上游，日後只要輸入 git push 即可。

🔑 注意：GitHub 已不支援密碼推送，需使用 Personal Access Token (PAT) 或 SSH Key。

📑 遠端追蹤分支 origin/main 緩衝機制

解開新手困惑：為什麼本機明明有 main，還會出現一個 origin/main？

唯讀書籤機制

本機上的「遠端投影」

• origin/main 存在於你的本機電腦中，它是一張唯讀的參照書籤。
• 離線時它記錄「上次與遠端通訊時，雲端 main 指在哪裡」。
• 執行 git fetch 會更新 origin/main；執行 git push 成功後它會滑向最新點。
• git pull 本質上就是 git fetch + git merge origin/main。

💡 安心心法：origin/main 就像遠端的一面鏡子，不小心手殘也不會破壞它！

🔄 日常同步三大資料流拓撲 (clone, pull, push)

團隊日常開發時，檔案與提交節點在本地與遠端間的流轉循環。

團隊同步黃金原則

先 Pull 再 Push

• 早晨第一件事：開始寫代碼前執行 git pull，確保以最新主線為基礎。
• 推送前保護傘：若別人先推了代碼，GitHub 會拒絕你的 push。此時應先 pull 合併最新進度，在本機解完衝突後再 push。

📌 口訣：「出發先 pull，收工前 push；衝突在本機解，別把破洞留給隊友」。

🤖 AI 輔助開發拓撲：GitHub Copilot 整合心法

人機協作時代的代碼產出流：精確註解 ➔ 幽靈文字 ➔ 人工審核入庫。

四大提效心法

1. 精準註解導引：提供明確的輸入輸出與情境規格。
2. 上下文完整：維持相關分頁開啟，讓 AI 理解全域型別。
3. 小步驗證：拆分單一責任小函式，易於 AI 精準產出。
4. 人為主導審核：AI 僅供草稿，開發者必須為邊界邏輯負全責。

⌨️ 快捷鍵：按 Tab 接受建議，按 Esc 拒絕，按 Alt + ] 查看下一組方案。

⚖️ 版本歷史整理的「黃金法則」

並非所有 Commit 都能隨意竄改，嚴格區分「本地」與「公共」是協作底線。

團隊協作底線

為什麼公共歷史不能 Reset？

• 嚴重後果：強行 reset 已推送的分支，會導致所有團隊成員的本機歷史脫節，造成毀滅性的重複衝突。
• 標準解法：線上若發現錯誤，請使用 git revert <Hash> 發布一筆新的「反向抵消」提交。

📌 黃金口訣：「未出門前隨便改，出了門後別後悔；公共歷史不用 reset，改用 revert 新增抵消」。

✏️ 歷史微調圖譜：commit --amend vs reset

剛按下 Commit 卻發現「標題寫錯字」或「漏加檔案」時的最優解法。

Reset 三大模式比較

• --soft：僅退回指標，修改完整保留在暫存區。
• --mixed（預設）：退回指標，修改回到工作區（未暫存）。
• --hard：毀滅模式，修改全部丟棄一乾二淨。
• 後悔救命藥：不慎 hard reset 可用 git reset --hard ORIG_HEAD 復原！

git commit --amend -m "fix: 正確的提交標題"

🛡️ PR 審查與 Squash Merge 拓撲壓縮

Pull Request 守門員機制與如何將繁瑣除錯節点壓扁為單一整潔提交。

團隊整潔度最佳實踐

Squash and Merge 價值

• 允許開發雜亂：工程師在功能分支上可以高頻隨意 commit。
• 確保主幹乾淨：合併時一鍵壓扁為單一完整 Commit，附帶 PR 編號。
• 利於回滾：未來若有 bug，可乾淨俐落地單鍵 revert 整個功能。

🤝 Code Review 禮儀：評論針對代碼本身、給予具體改進範例、多讚美優秀設計。

📐 三大團隊分支工作流拓撲對比

Git Flow（傳統嚴謹）vs GitHub Flow（極簡敏捷）vs GitLab Flow（環境優先）。

選型建議矩陣

• GitHub Flow（推薦首選）：只有一個 main 主幹，隨時保持可部署狀態。功能由 feature 分支經由 PR 審查合併。
• Git Flow：適合有固定「版本週期發布（如 v1.0, v2.0）」的傳統大型軟體。
• GitLab Flow：適合 SaaS 具備「開發/預發/正式」多部署環境的架構。

💡 原則：現代團隊協作「越簡單越好」，非必要勿盲目套用過度繁瑣的 Git Flow！
