🌿 第 01 章

Git 核心架構：三大空間與版本快照

版本控制的起點：告別單鍵覆蓋的恐懼，理解每次 Commit 背後的時間快照機制與分段確認心智模型。

1.1 傳統單鍵儲存 (Ctrl+S) 的三大致命缺點

❌ 傳統覆蓋備份的痛點：
  • 狀態單一且不可逆：檔案一儲存，前一版邏輯直接蒸發。
  • 檔名極度混亂：產生 專案_最終版_v2_定稿.zip 等命名災難。
  • 責任不明：團隊協作時無法查證「何人、何時、為何」修改該行代碼。
✅ Git 快照機制的解法：
  • 精準挑選變更：透過「暫存區」過濾變更，維持乾淨歷史。
  • 不可篡改快照：每次提交皆由 SHA 雜湊校驗保護，歷程完整。
  • 平行時空實驗：隨意開分支測試，失敗一鍵回滾安全節點。

1.2 三大工作空間職責劃分

理解這三個區域的職責分工，就能掌握 Git 80% 的日常檔案操作流向：

空間 1

工作區 (Working Tree)

日常修改工作桌：在 VS Code 編輯器裡直接修改的實體檔案。在執行 git add 前屬於 Modified 狀態。

空間 2

暫存區 (Staging Area)

寄件打包裝箱台：挑選要包含於下一次提交的變更清單。狀態為 Staged，維持提交內容純粹。

空間 3

版本庫 (Repository)

永久快照倉庫 (.git)：執行 git commit 後永久保存的不可變歷史節點，狀態為 Committed。

💡 生活化比喻：把暫存區想像成「寄快遞前的打包箱」。你在房間桌面（工作區）塗塗改改，只有被你親手放進箱子裡的檔案，才會在蓋上封條（Commit）時被永遠存檔發送。

1.3 標準日常開發三步曲指令

每當完成一個獨立的小邏輯變更時，依序執行的標準工作流：

Terminal — Daily 3 Steps 
# 步驟 1：檢視目前工作區與暫存區狀態（確認哪些檔案有變更）
git status

# 步驟 2：將指定檔案（或當前目錄全部檔案）加入暫存區打包箱
git add <檔案名稱>    # 挑選單一檔案
git add .             # 將當前目錄下所有新增與修改批次暫存

# 步驟 3：將暫存區的檔案正式封裝為快照節點，並附上具體說明
git commit -m "feat: 完成使用者登入頁面排版"

# 輔助：檢視簡要版本歷史紀錄
git log --oneline
⚠️ 新手防雷避坑錦囊：
  • add 後又改程式碼？ git add 只會捕捉執行的那一瞬間！後續修改必須再次執行 git add 才能納入 Commit。
  • 誤入黑底 Vim 編輯器？ 輸入 git commit 漏加 -m 參數時會跳入 Vim。別慌張！按鍵盤 Esc，依序輸入 :wq 再按 Enter 即可存檔離開。
🌿 第 02 章

Git 分支與合併實戰：指針原理與衝突排查

多工平行開發的關鍵機制：理解分支 40 字元輕量指針的本質、兩種合併模式差異，並掌握手動解決衝突的標準 SOP。

2.1 分支的本質：不是檔案複製，而是「可移動的書籤指針」

在傳統版控中，開分支需要複製整包專案（幾百 MB 磁碟空間）；而在 Git 中，建立分支只是在 .git/refs/heads/ 檔案中寫入一個 41 位元組的文字檔案，指向特定 Commit 的 SHA 雜湊！

圖 2-1：分支結構圖 — HEAD 聚光燈指向目前工作的 iss53 分支
💡 HEAD 的角色：把 HEAD 當作「當前工作舞台上的聚光燈」。你在哪個分支上工作，聚光燈就打在該分支最新節點上。當你 commit 時，該分支與 HEAD 指針會自動往前滑動一步。

2.2 現代分支操作推薦指令

Terminal — Branch Management 
# 1. 建立新分支並同時切換過去（現代版指令，推薦使用）
git switch -c feature/login      # 等同經典 git checkout -b feature/login

# 2. 安全切換回已存在的主幹分支（切換前確保工作區已 commit 或 stash）
git switch main                  # 等同經典 git checkout main

# 3. 檢視本地所有分支清單（包含最新提交摘要）
git branch -v

# 4. 安全刪除已合併完成的分支（保持分支清單清爽）
git branch -d feature/login

2.3 兩種合併模式深度剖析

模式 1

快進合併 (Fast-forward)

• 觸發情境：兩分支**沒有分岔**，被合併分支的提交能直線追溯回目前分支。
• 動作機制：Git 直接將 main 指標向前滑動到最新節點。
• 結果：不產生額外的新 Commit 節點，歷史保持單一直線。

模式 2

三方合併 (3-way Merge)

• 觸發情境：歷史**已出現分岔**，兩分支各自累積了獨立的 Commit。
• 動作機制：Git 找出兩者的「共同祖先 (Ancestor)」，計算三方差異。
• 結果：自動生成具備兩個親代（Parents）的全新「合併提交（Merge Commit）」。

2.4 合併衝突排查：標記語法與四步標準解法

當兩個分支修改了同一個檔案的相同行數時，Git 無法猜測誰才是對的，會暫停合併並在檔案中寫入**衝突標記**：

衝突標記語法解析 (Merge Conflict Syntax) 
<<<<<<< HEAD （這是你目前所在分支的代碼）
console.log("購物車總額優惠價: " + discountPrice);
======= （分隔線）
console.log("購物車總額會員價: " + memberPrice);
>>>>>>> feature/member （這是傳入分支的修改）
🛠️ 手動解決衝突標準 4 步驟：
  1. 定位衝突：輸入 git status 查看標記為 both modified 的檔案。
  2. 手動裁決：開啟檔案，刪除 <<<<<<<、=======、>>>>>>> 標記，保留正確的商業邏輯。
  3. 標記已解決：執行 git add <檔案名稱> 將修復完成的檔案加入暫存區。
  4. 完成合併：執行 git commit，Git 會自動填入預設的 Merge Commit 訊息並完成入庫！
☁️ 第 03 章

GitHub 遠端協作：倉庫關聯與推送流程

跨出個人本機端：理解分散式版本控制本機與雲端的職責分工、初次推送標準 6 步驟與 GitHub Copilot 輔助開發心法。

3.1 Git 工具 vs GitHub 平台架構差異

Git 本機版本控制 (VCS)

• 純本機運作：由 Linus Torvalds 開發，無需網路即可完整建立 Commit 快照與分支。
• 職責：管理你電腦硬碟中具體目錄的檔案歷程引擎。

GitHub 雲端協作平台

• 雲端中央託管：提供公開或私有的遠端儲存庫（Remote Repository）。
• 職責：支援 Pull Request（代碼審查）、Issue、CI/CD 與開源社群。

3.2 首次推送本機專案上 GitHub：標準 6 步驟

Terminal — First Push Workflow 
# 步驟 1：專案根目錄初始化 Git 儲存庫
git init

# 步驟 2：將所有初始檔案加入暫存區
git add .

# 步驟 3：建立專案的第一次版本提交
git commit -m "feat: initial commit"

# 步驟 4：將本地主分支重新命名為現代標準的 main
git branch -M main

# 步驟 5：新增名為 origin 的遠端伺服器連結（請替換為你的倉庫網址）
git remote add origin https://github.com/username/project.git

# 步驟 6：推送本地 main 分支至遠端，並設定 upstream 追蹤關聯 (-u)
git push -u origin main
💡 什麼是 -u？ -u（即 --set-upstream）代表將本地 main 與遠端 origin/main 綁定追蹤。日後在該分支只需輸入極簡的 git push 或 git pull，Git 就知道該向哪個遠端端點同步！

3.3 遠端日常同步三部曲

git clone <url>

首次下載完整遠端倉庫至全新資料夾，自動建立 origin 關聯。

git pull

下載夥伴的最新 Commit 並立即合併至當前工作分支。

git push

將本地已經 Commit 的全新快照節點上傳同步至遠端倉庫。

3.4 AI 輔助開發心法：GitHub Copilot 實務指南

⌨️ 核心互動快捷鍵：

寫程式碼時編輯器會自動跳出灰色幽靈代碼：
• 按 Tab：一鍵採納建議代碼。
• 按 Esc：拒絕建議，維持手動輸入。

🎯 四大 Copilot 提效心法：

1. 註解精確導引：寫出清楚的函式名稱與註解。
2. 上下文完整：維持關聯檔案開啟，提供型別資訊。
3. 小步驗證：拆分單一責任小函式，利於 AI 生成。
4. 人為主導審查：AI 代碼僅為參考，嚴格檢查邊界條件。

⏱️ 第 04 章

版本回溯與救援手冊：Reset、Amend 與 Stash

版本控制的時光機器：掌握歷史修訂黃金法則、撤銷提交的 Soft/Hard 模式對照，以及 ORIG_HEAD 與 Stash 救命小抽屜。

4.1 版本歷史修訂的「黃金法則」

🟢 本地未推送（Local Only）：自由整理

只要你的 Commit 還沒 git push 到公共遠端，你可以隨意使用 amend、reset 打理出最優雅整潔的提交歷史，消除除錯贅言。

🔴 已推送遠端（Public Remote）：嚴禁竄改！

絕對不要對已經發布至遠端的分支重寫歷史（如 git push -f）。這會導致隊友的歷史節點嚴重脫節！若線上代碼有錯，請使用 git revert 發布一筆新的「反向抵消」提交。

📌 一句話口訣：「未出門前隨便改，出了門後別後悔；公共歷史不用 reset，改用 revert 新增抵消」。

4.2 微調最後一次提交：git commit --amend

剛按下 Commit 卻發現「標題寫錯字」或「漏加一個小檔案」時的最優解法：

Terminal — Commit Amend 
# 情境 1：剛提交完，只想修正提交標題訊息
git commit --amend -m "fix: 修正正確的登入表單驗證"

# 情境 2：剛提交完，發現漏抓了一個設定檔，想補塞進剛才的提交中
git add config.json
git commit --amend --no-edit     # --no-edit 代表維持原本的提交標題不變

4.3 撤銷提交：git reset --soft vs --hard 深度對照

git reset 能夠將 HEAD 指標向後移動至先前節點（例如 HEAD^ 代表前一個版本）：

溫和模式

git reset --soft "HEAD^"

• HEAD 指標：退回前一個版本。
• 暫存區與工作區：完整保留！最後一次 Commit 的變更依然停留在 Staged 狀態。
• 適用時機：想要重新撰寫提交訊息，或把最後兩次提交合併為一次時。

強硬重置

git reset --hard "HEAD^"

• HEAD 指標：退回前一個版本。
• 暫存區與工作區：全部抹除！工作區所有未保存與已提交改動全部被丟棄。
• 適用時機：確認最後一次改動是完全失敗的實驗，徹底放棄回歸乾淨狀態。

🛟 救命後悔藥：git reset --hard ORIG_HEAD
若執行 --hard 後突然反悔，別慌！Git 在執行危險操作前會將原本 HEAD 存於 ORIG_HEAD。立即執行此指令即可 1 秒還原！此外被 reset 掉的 Commit 依然躺在 .git/objects/ 內，使用 git reflog 隨時可救回！

4.4 臨時工作抽屜：git stash

手邊工作進行到一半被臨時插單修復緊急 Bug？將半成品存入臨時工作抽屜：

git stash

將工作區所有未提交的修改收入抽屜，工作區瞬間恢復乾淨。

git stash list

檢視目前抽屜裡所有堆疊的進度清單（如 stash@{0}）。

git stash pop

取回最新一筆暫存進度並還原至工作目錄，同時自抽屜刪除。

👥 第 05 章

GitHub 團隊協作與分支工作流

現代軟體工程的團隊基石：Pull Request 審查機制、Squash and Merge 歷程壓縮技巧，以及三大分支策略深度評析。

5.1 什麼是 Pull Request (PR)？代碼品質的最後守門員

在團隊開發中，嚴禁直接向 main 主幹分支推送代碼。任何功能皆須在獨立分支（如 feature/login）完成開發並推送到遠端後，向專案負責人發起「請求合併（Pull Request）」。

💬 行內精準討論

審查者可直接在特定程式碼行數提出優化建議與範例。

🛡️ CI/CD 自動化守門

自動執行單元測試與安全掃描，全數通過才解鎖合併。

🔗 任務自動結案

在 PR 說明中加入 Closes #53，合併時自動關閉關聯 Issue。

5.2 開立 PR 四步驟與 Code Review 建設性審查禮儀

📋 開立 PR 標準四步驟：
  1. Compare：選定 base: main ← compare: feature 分支。
  2. Title：撰寫清楚的語義前綴（如 feat: 購物車結帳流程）。
  3. Context：交代「為什麼要改」並附上測試驗證截圖。
  4. Reviewers：指定相關模組負責人作為審查者。
🤝 Code Review 建設性審查守則：
  • 對事不對人：聚焦代碼邊界條件，而非評價作者技術。
  • 給予具體範例：指出問題同時，附上建議的替換代碼。
  • 善用標籤前綴：例如 [nit]（小細節）、[blocking]（必須修正）。
  • 肯定夥伴付出：看到優秀的重構時，留個 👏 給予讚美。

5.3 Squash and Merge 歷程壓縮合併技巧

一般合併的缺點：

開發期間產生的 fix: typo、debug again 等零散瑣碎 commit 會全數混入主幹，導致主幹歷程極度雜亂。

Squash and Merge 的效益：

GitHub 在合併瞬間將該 PR 的所有 Commit 壓縮打包成單一乾淨節點併入主幹。日後線上若有重大意外，git revert 一鍵即可乾淨撤除該功能！

5.4 三大團隊分支工作流全面評析

傳統多軌

Git Flow

• 分支：master, develop, feature, release, hotfix。
• 適用：有明確版本發布週期（如 v1.0, v2.0）的傳統大型軟體。
• 缺點：分支繁瑣，易漏合雙主幹。

現代敏捷

GitHub Flow

• 分支：只有 main 主幹 + 敘述性 feature 分支。
• 特色：以 PR 為核心，main 永遠保持可部署狀態。
• 適用：SaaS、Web 應用與持續交付 (CD)。

上游優先

GitLab Flow

• 分支：master + 各環境分支 (pre-prod / prod)。
• 特色：上游優先（Upstream First），所有代碼由 master 依序單向流入生產。
• 適用：多伺服器環境企業架構。

🏁 第 06 章

核心心法總結與日常速查清單

恭喜完成全篇學習！在此為你濃縮全講義四柱核心心智模型與日常高頻指令速查表。

6.1 Git & GitHub 四大支柱心智模型

1. 三大空間分段確認

工作區修訂 → 暫存區打包 → 版本庫永久存檔。每次 commit 只封裝單一職責邏輯。

2. 分支輕量勇敢開拓

分支只是 40 字元指針！勇敢建立 Feature 分支進行實驗，切換前維持工作區乾淨。

3. 遠端同步慎防竄改

本地未推送自由整理；一旦 push 遠端，公共歷史神聖不可竄改，線上錯誤一律用 revert。

4. 團隊協作嚴格把關

開立 PR 進行同儕審查，善用 Squash and merge 維持主幹歷史清晰。

功能驅動開分支，
微小改動立提交；
開立 PR 做審核，
Squash 壓縮保乾淨！
